# DreamBank 단계별 개발 계획

## 1. 계획의 기준과 범위

이 문서는 다음 두 문서를 실제 개발 작업 단위로 구체화한 실행 계획이다.

- [기능 및 제품 개발 프롬프트](development-prompt.md)
- [기술 스펙 및 아키텍처 지침](development-technical-spec.md)

제품의 기능과 감성적 경험은 기능 문서를 따르고, 기술 선택과 구현·검증 기준은 기술 스펙을 따른다. 기술 스택은 Flutter/Dart, Material 3 기반 커스텀 UI, Riverpod, go_router, SQLite/Drift, shared_preferences를 사용한다. 정확한 SDK 및 패키지 버전은 환경 확인과 호환성 검증 후 확정한다.

이번 범위는 Android와 iOS에서 동작하는 로컬 우선 MVP다. P0를 검증한 뒤 P1을 구현한다. 로그인, 백엔드, 실제 금융 연동, 클라우드 동기화, 푸시 알림, 소셜 기능 및 P2 기능은 제외한다.

현재 확인된 프로젝트 파일은 두 기준 문서이며, 실행 가능한 앱이나 개발 환경의 정상 동작은 아직 검증하지 않았다. 아래 결과물과 완료 기준은 앞으로 수행할 작업이며 완료 보고를 의미하지 않는다.

## 2. 전체 진행 순서

| 단계 | 구분 | 핵심 목표 | 주요 결과물 | 다음 단계 진입 조건 |
|---|---|---|---|---|
| 01 | 준비 | 개발 환경과 빌드 가능 범위 확인 | 환경 점검 보고서 | 사용 SDK와 플랫폼별 제약 확인 |
| 02 | 설계 | 화면·데이터·동작 규칙 확정 | MVP 설계 문서 | 기능별 저장 및 화면 흐름 정의 |
| 03 | 기반 | 두 플랫폼의 앱 골격 구성 | Flutter 프로젝트와 기본 내비게이션 | 4개 탭 이동 및 초기 실행 확인 |
| 04 | 기반 | 로컬 영속 저장과 데이터 흐름 구성 | Drift DB, Repository, Provider | 초기화·CRUD·재조회 테스트 통과 |
| 05 | P0 | 가상 계좌와 감성 홈 구현 | 홈·마음 잔고·계좌 설정 | P0 사용자 흐름 동작 |
| 06 | P0 검증 | 기본 앱의 안정성과 빌드 확인 | P0 검증 보고서 | 오류 수정 및 플랫폼별 결과 기록 |
| 07 | P1 | 꿈 보관함 완성 | 꿈 CRUD 화면과 테스트 | 저장·수정·삭제·재실행 검증 |
| 08 | P1 | 미래의 편지 완성 | 편지 CRUD와 공개일 처리 | 날짜 경계·재조회 검증 |
| 09 | P1 | 공유 카드 이미지와 OS 공유 완성 | 카드 렌더러·공유 어댑터 | 이미지 생성 및 공유 동작 확인 |
| 10 | 통합 검증 | 전체 경험과 양 플랫폼 빌드 검증 | 최종 검증 보고서·빌드 산출물 | 완료 조건별 근거 확보 |
| 11 | 인계 | 재현 가능한 실행과 후속 작업 정리 | README·완료 보고서 | 실행 절차 및 제한 사항 명시 |

단계별로 변경 파일, 실행 명령, 테스트·빌드 결과, 미해결 항목을 기록한다. 검증 실패는 해당 단계에서 수정한 뒤 다음 단계로 진행한다. 외부 환경이나 서명 문제로 진행할 수 없는 검증은 사유와 재개 조건을 기록하고 독립적인 개발 작업을 계속한다. 미실행 검증을 통과로 처리하지 않는다.

## 3. 단계별 실행 계획

### Step 01. 개발 환경 및 프로젝트 상태 조사

**목표:** Flutter 개발과 Android·iOS 검증을 수행할 수 있는지 확인하고 사용할 버전을 확정한다.

**구체 작업**

1. 기존 파일, Git 상태, 프로젝트 지침 및 설치된 도구를 확인한다.
2. Flutter/Dart 버전과 `flutter doctor -v` 결과를 확인한다.
3. Android SDK, JDK, 에뮬레이터 또는 연결 기기 상태를 확인한다.
4. Xcode, 명령행 개발 도구, CocoaPods 등 필요한 iOS 도구와 시뮬레이터 상태를 확인한다.
5. 필수 패키지의 유지보수 상태, 라이선스, 플랫폼 지원, SDK 호환성을 공식 자료로 확인한다.
6. 사용 가능한 환경과 추가 설치·설정이 필요한 항목을 구분한다. 패키지 식별자는 임시 개발용인지 최종 출시용인지 명시한다.

**결과물**

- `docs/environment-report.md`: 도구 버전, 점검 결과, 기기 목록, 제약 및 해결 작업.
- 사용할 Flutter/Dart 버전과 초기 의존성 후보 목록.

**완료 기준:** Android와 iOS 각각의 실행·빌드 가능 여부를 설명할 수 있고, 환경 문제의 해결 순서가 정해져 있다.

### Step 02. 화면, 데이터 모델 및 동작 규칙 설계

**목표:** 구현 과정에서 서로 다른 해석이 생기지 않도록 MVP의 구체적인 동작을 정한다.

**구체 작업**

1. 홈 / 꿈 보관함 / 미래의 편지 / 내 계좌의 화면 구성과 상세 화면·편집 화면의 이동 경로를 정의한다.
2. 각 화면의 기본, 로딩, 빈 목록, 오류, 저장 중 상태와 사용자 피드백을 정한다.
3. AccountSettings, MoodEntry, DreamItem, FutureLetter, AppSettings의 필드 타입, 필수 여부, 기본값과 저장 위치를 정의한다.
4. 원화 잔고와 예상 비용은 정수 원 단위로 취급하고, 잘못된 금액 입력·빈 제목·과도한 길이 등 입력 검증 규칙을 정한다.
5. 계좌 별칭 편집과 가상 잔고 설정의 범위를 정한다. 기본 잔고는 10억 원이며 꿈의 예상 비용과 연결하지 않는다.
6. 마음 상태의 저장 시점과 메시지 선택 규칙을 정한다. 선택을 건너뛸 수 있고, 다른 메시지 버튼은 가능한 한 현재와 다른 메시지를 보여준다.
7. 편지 공개일은 기기 현지 날짜를 기준으로 선택일 00:00부터 열람하는 규칙으로 설계한다. 공개일 미지정은 즉시 열람으로 처리한다. 날짜의 저장·변환 방식, 잠긴 편지의 목록·편집 노출 범위, 삭제 동작을 명시한다.
8. 편지의 날짜 잠금은 앱 내 표시 규칙이며 보안 암호화 기능은 아니라는 점을 앱 설명에 반영한다.
9. 색상, 간격, 타이포그래피, 라운드, 터치 영역, 애니메이션과 접근성 기준을 정의한다. 초기 테마 범위와 설정 노출 항목도 확정한다.

**결과물**

- `docs/mvp-design.md`: 화면 흐름, 입력 검증, 메시지·공개일 규칙, 디자인 토큰.
- `docs/data-model.md`: 필드·기본값·인덱스·저장소·스키마 버전 및 마이그레이션 방침.
- 기능별 인수 조건과 테스트 대응표.

**완료 기준:** 모든 MVP 기능에 화면 진입점, 데이터 저장 위치, 오류 처리와 검증 기준이 연결되어 있다.

### Step 03. Flutter 프로젝트 및 앱 기반 구성

**목표:** 실제 실행 가능한 앱에 공통 구조와 디자인 시스템을 만든다.

**구체 작업**

1. Android·iOS를 지원하는 Flutter 프로젝트를 생성하고 의존성과 잠금 파일을 관리한다.
2. `app`, `core`, `features`, `data/database`, `data/repositories`와 테스트 디렉터리를 구성한다. 사용하지 않는 계층이나 빈 추상화는 만들지 않는다.
3. Riverpod의 앱 진입점과 go_router의 하단 탭 구조를 설정한다. 탭 전환 시 필요한 화면 상태를 유지한다.
4. 딥 네이비·골드·아이보리 기반 테마, 공통 카드·버튼·입력 폼·상태 표시 위젯을 구현한다.
5. SafeArea, 키보드 표시, 스크롤 및 시스템 글자 크기를 고려한 기본 레이아웃을 구성한다.
6. 간결한 DreamBank 로고와 기본 앱 아이콘을 준비하고 플랫폼 표시 이름을 설정한다.

**결과물**

- Flutter 프로젝트, `pubspec.yaml`, `pubspec.lock`, Android·iOS 프로젝트 설정.
- 앱 테마와 공통 UI, 4개 탭 내비게이션.
- 탭 이동과 기본 화면 렌더링을 확인하는 위젯 테스트.

**완료 기준:** 사용 가능한 기기에서 앱이 실행되고 탭을 이동할 수 있으며, 기본 정적 분석과 위젯 테스트가 통과한다.

### Step 04. 로컬 저장소 및 Repository 구현

**목표:** 앱을 종료해도 유지되는 데이터 기반을 먼저 검증한다.

**구체 작업**

1. Drift 테이블, 데이터베이스 연결, 스키마 버전, 초기화 트랜잭션을 구현한다.
2. 기본 계좌를 한 번만 생성한다. 별칭은 `나의 여유 계좌`, 잔고는 `1000000000`, 통화는 `KRW`로 설정한다.
3. 계좌, 마음 기록, 꿈, 편지의 조회·변경 Repository를 구현하고 Riverpod에 연결한다.
4. 간단한 앱 설정은 shared_preferences로 분리한다. 화면 위젯이 저장소를 직접 호출하지 않게 한다.
5. 저장·조회 실패를 UI가 처리할 수 있는 형태로 전달하고 사용자 텍스트를 오류 로그에 남기지 않는다.
6. 초기 스키마 테스트와 향후 마이그레이션 테스트의 기반을 마련한다. 실제 스키마 변경 시 데이터 보존 테스트를 추가한다.

**결과물**

- Drift 스키마 및 생성 코드, Repository, 설정 저장소, Provider.
- 초기화 중복 방지, CRUD, 연결 종료 후 재연결·재조회, 오류 전달 단위 테스트.

**완료 기준:** 기본 데이터가 중복 생성되지 않고, 파일 기반 DB를 다시 열어도 변경 내용이 유지되며 관련 테스트가 통과한다.

### Step 05. P0 사용자 경험 구현

**목표:** 가상 계좌와 위로 메시지, 마음 선택을 실제로 사용할 수 있게 한다.

**구체 작업**

1. 홈에 브랜드, 인사말, 가장 크게 강조한 가상 잔고 카드와 꿈 보관함 진입점을 배치한다.
2. `가상 잔고` 표시와 실제 금융 서비스가 아니라는 설명을 제공한다.
3. 여러 기본 메시지와 기분별 메시지를 준비하고 다른 메시지 보기 동작을 구현한다.
4. 네 가지 마음 상태 선택, 기록 저장, 선택에 따른 메시지 변경을 구현한다.
5. 내 계좌에서 별칭을 수정하고 홈에도 반영한다. 확정한 범위에 따라 가상 잔고 설정 및 최소 앱 설정을 구현한다.
6. 저장 중 중복 입력 방지, 저장 완료 피드백과 실패 시 재시도 동작을 제공한다.

**결과물**

- 동작하는 홈, 마음 선택, 계좌 편집 화면.
- 통화 표시·메시지 선택 단위 테스트와 잔고 표시·마음 선택·별칭 편집 위젯 테스트.

**완료 기준:** 기본 잔고가 `₩1,000,000,000`으로 표시되고, 마음에 맞는 메시지를 볼 수 있으며 계좌 설정과 마음 기록이 재실행 후 유지된다.

### Step 06. P0 검증 및 안정화

**목표:** P1을 추가하기 전에 앱 기반의 오류를 해결한다.

**구체 작업**

1. 코드 포맷 검사, `flutter analyze`, 단위·위젯 테스트를 실행한다.
2. 최초 실행 → 마음 선택 → 메시지 변경 → 별칭 수정 → 앱 종료·재실행 흐름을 확인한다.
3. 작은 화면과 확대된 글자에서 잔고·버튼·하단 탭의 잘림과 겹침을 확인한다.
4. Android 디버그 빌드와 사용 가능한 환경의 iOS 시뮬레이터 빌드·실행을 검증한다.
5. 실패 항목을 수정하고 영향받은 검증을 다시 수행한다.

**결과물:** `docs/verification-p0.md`와 플랫폼별 빌드 결과, 수정된 P0 앱.

**완료 기준:** P0 기능 테스트와 정적 분석이 통과하며, 플랫폼별 빌드·실행 결과가 실제 증거와 함께 기록되어 있다. 환경으로 막힌 항목은 미검증으로 남긴다.

### Step 07. 꿈 보관함 구현

**목표:** 사용자가 꿈과 선택적인 예상 비용을 자유롭게 관리한다.

**구체 작업**

1. 꿈 목록과 빈 상태, 추가 진입점 및 상세·편집 화면을 구현한다.
2. 제목·설명·선택 비용 입력, 수정, 삭제와 삭제 확인을 구현한다.
3. 입력 검증, 저장 중 상태, 실패 피드백 및 저장 후 목록 갱신을 연결한다.
4. 예상 비용이 계좌 잔고를 바꾸지 않도록 데이터와 동작을 분리한다.

**결과물:** 꿈 CRUD 화면, Repository 연동, 입력·CRUD 및 목록 갱신 테스트.

**완료 기준:** 비용 없는 꿈과 비용 있는 꿈 모두 생성·수정·삭제할 수 있고 재실행 후 유지되며 가상 잔고에 영향이 없다.

### Step 08. 미래의 편지 구현

**목표:** 편지 작성과 공개 날짜에 따른 열람 경험을 완성한다.

**구체 작업**

1. 편지 목록, 작성·편집·삭제와 상세 화면을 구현한다.
2. 작성일과 공개 날짜를 저장하고 열람 가능·공개 예정 상태를 구분한다.
3. 확정한 공개일 규칙을 적용하고, 앱 재진입·날짜 변경 후 열람 상태를 다시 계산한다.
4. 날짜 판정 로직에 현재 시각을 주입할 수 있게 하여 테스트를 안정적으로 수행한다.
5. 편집을 포함한 잠긴 편지의 콘텐츠 노출을 Step 02 규칙과 일치시킨다.

**결과물:** 편지 CRUD 화면, 날짜 판정 로직, 날짜 경계·미지정 날짜·목록 상태 테스트.

**완료 기준:** 생성·수정·삭제와 재조회가 동작하고, 공개일 전후 상태가 설계한 규칙대로 바뀐다.

### Step 09. 가상 계좌 카드 생성 및 공유

**목표:** 실제 계좌로 오인되지 않는 카드 이미지를 운영체제 공유 기능으로 전달한다.

**구체 작업**

1. 내 계좌에 공유 카드 미리보기와 공유 버튼을 추가한다.
2. 브랜드, 별칭, 잔고, 짧은 문구, `가상 잔고` 표시를 가진 공통 카드 UI를 구현한다.
3. 카드 렌더링을 이미지로 변환하고 임시 파일에 저장한다.
4. 이미지 생성 서비스와 OS 공유 어댑터를 분리한다. 공유 플러그인은 Step 01의 기준으로 선택한다.
5. 이미지 생성 실패·공유 취소·반복 탭을 처리하고 임시 파일 정리 정책을 적용한다. 공유 대상 앱이 읽기 전에 파일이 삭제되지 않도록 한다.
6. 긴 별칭, 큰 글자, 숫자 표시 및 화면과 이미지의 내용 일치를 확인한다.

**결과물:** 공유 카드 UI, 이미지 생성 서비스, 공유 어댑터, 이미지 생성 테스트 및 플랫폼별 수동 검증 기록.

**완료 기준:** 읽을 수 있는 이미지 파일이 생성되고, Android·iOS에서 공유 시트와 이미지 전달을 각각 확인한다. 공유 취소 후 앱을 정상적으로 사용할 수 있다.

### Step 10. 전체 통합 검증 및 릴리스 준비

**목표:** 모든 완료 조건의 충족 여부를 실제 테스트와 빌드로 확인한다.

**구체 작업**

1. 포맷, 정적 분석, 전체 단위·위젯 테스트를 수행한다.
2. 최초 실행, 꿈 저장 후 재실행, 편지 재조회, 계좌 수정, 카드 생성을 통합 테스트로 검증한다.
3. 작은 화면·큰 화면·글자 확대·키보드·접근성·앱 재진입 시 UI를 확인한다.
4. 오류·빈 상태와 저장 실패 피드백을 확인하고 불필요한 로그·의존성·코드를 정리한다.
5. Android 디버그 빌드 및 릴리스 APK 또는 AAB 생성을 검증한다. 개발용 서명과 출시용 서명을 구분하고 비밀 정보를 저장소에서 제외한다.
6. iOS 시뮬레이터 빌드·실행과 릴리스 빌드 가능 범위를 확인한다. 배포용 아카이브는 계정·식별자·서명이 준비된 경우 검증하고, 그렇지 않으면 필요한 설정과 미검증 범위를 기록한다.
7. 각 플랫폼의 실제 기기 검증 여부를 별도로 기록한다. 시뮬레이터 결과를 실기기 결과로 간주하지 않는다.
8. 기능 문서의 완료 조건 각각을 테스트·수동 확인·빌드 결과에 연결한다.

**결과물**

- `docs/verification-final.md`: 명령, 결과, 검증 환경, 완료 조건 대응표와 알려진 문제.
- 실제 생성된 Android 빌드 산출물 및 가능한 iOS 빌드 산출물의 위치.
- 출시 계정·서명·실기기 검증 등 남은 작업 목록.

**완료 기준:** 전체 테스트와 정적 분석이 통과하고 양 플랫폼 빌드 결과가 구분되어 있다. 필수 기능의 실패는 수정한다. 미검증 항목이 있으면 전체 검증 완료로 보고하지 않는다.

### Step 11. 실행 문서와 최종 인계

**목표:** 동일한 환경에서 앱을 다시 실행하고 유지보수할 수 있도록 한다.

**구체 작업**

1. SDK·도구 버전, 의존성 설치, Drift 코드 생성, 앱 실행, 테스트, 플랫폼별 빌드 명령을 정리한다.
2. 실제 프로젝트 구조, 데이터베이스 테이블과 마이그레이션 절차를 문서와 일치시킨다.
3. 로컬 저장 특성, 앱 삭제 시 데이터 손실 가능성, 실제 금융 서비스가 아니라는 앱 안내를 확인한다.
4. 구현 기능, 검증 결과, 알려진 문제와 스토어 출시 전 필요한 작업을 보고한다.
5. CI는 로컬 구현과 빌드가 완료된 뒤 필요하면 최소 범위로 구성한다. 추가 여부와 이유를 기록한다.

**결과물:** `README.md`, 최신 데이터 모델 문서, `docs/completion-report.md`. 필요한 경우 최소 CI 설정.

**완료 기준:** 문서의 명령으로 개발·검증 절차를 재현할 수 있고, 구현 완료와 플랫폼 검증 완료 및 스토어 출시 준비 상태가 명확하게 구분된다.

## 5. 단계별 기록 양식

각 검증 보고서는 다음 항목을 포함한다.

- 수행 단계와 대상 커밋 또는 코드 상태
- 변경 파일과 구현된 사용자 동작
- 도구·플랫폼·기기 버전
- 실행한 명령과 결과: 통과 / 실패 / 미실행
- 수동 확인한 흐름과 관찰 결과
- 발견한 문제, 수정 내용과 재검증 결과
- 미해결 항목, 사용자에게 미치는 영향과 다음 조치

개발 일정은 Step 01의 환경 조사 후 산정한다. 먼저 P0 실행과 검증을 중간 결과물로 확보하고, P1 완료 후 전체 플랫폼 검증과 인계를 진행한다.
