# DreamBank 개발 기술 스펙 및 아키텍처 지침

앞서 정의한 DreamBank의 기능 명세를 기준으로 Android와 iOS를 동시에 지원하는 실제 모바일 앱을 개발하라.

이번 작업에서는 기능 목록을 다시 기획하는 것이 아니라, 프로젝트의 기술 스택, 아키텍처, 데이터 관리, 코드 품질, 테스트, 빌드 및 배포 기준을 명확하게 정의하고 실제 프로젝트에 적용하는 것이 목적이다.

## 1. 필수 기술 스택

다음 기술 스택을 기본으로 사용한다.

| 구분 | 기술 | 용도 |
|---|---|---|
| 모바일 프레임워크 | Flutter | Android·iOS 통합 개발 |
| 프로그래밍 언어 | Dart | 애플리케이션 로직 |
| UI | Flutter Material 3 기반 커스텀 UI | 플랫폼 간 일관된 디자인 |
| 상태 관리 | Riverpod | 화면 상태와 비즈니스 로직 관리 |
| 라우팅 | go_router | 화면 이동 및 라우트 관리 |
| 로컬 데이터베이스 | SQLite + Drift | 구조화된 사용자 데이터 저장 |
| 간단한 설정 저장 | shared_preferences | 테마 및 간단한 앱 설정 |
| 날짜 및 시간 | Dart 기본 API 우선 | 날짜 처리 |
| 이미지 공유 | Flutter 플러그인 활용 | 가상 계좌 카드 이미지 생성 및 공유 |
| 테스트 | flutter_test | 단위·위젯 테스트 |
| 정적 분석 | flutter analyze | 코드 품질 검증 |
| 버전 관리 | Git | 변경 이력 및 작업 관리 |

의존성은 필요한 경우에만 추가한다. 패키지를 선택할 때는 현재 유지보수 상태, Android·iOS 지원 여부, 라이선스 및 최신 호환성을 확인한다.

버전 번호는 임의로 고정하지 말고, 실제 개발 환경에 설치된 Flutter SDK와 호환되는 안정 버전을 확인해 사용한다. 의존성 버전은 프로젝트 설정 파일과 잠금 파일로 관리한다.

## 2. 크로스플랫폼 개발 원칙

- 하나의 Flutter 코드베이스에서 Android와 iOS를 모두 지원한다.
- 플랫폼별로 같은 기능을 별도 구현하지 않는다.
- 공통 UI와 비즈니스 로직을 최대한 공유한다.
- 플랫폼별 차이가 필요한 기능은 별도 어댑터 또는 플랫폼 분기 로직으로 격리한다.
- Android와 iOS에서 동일한 주요 기능과 데이터 구조를 제공한다.
- 화면 크기, 안전 영역, 키보드, 시스템 내비게이션, 다크 모드 및 접근성을 고려한다.
- 플랫폼별 디자인 차이는 필요한 경우에만 적용하고, 전체 브랜드 경험은 일관되게 유지한다.

iOS 빌드 및 서명에는 macOS와 Xcode가 필요하다는 점을 고려한다.

## 3. 아키텍처

기능별 책임을 분리하는 단순한 계층형 구조를 사용한다.

- Presentation: 화면, 위젯, UI 상태
- Application: 사용자 동작과 기능 흐름을 처리하는 컨트롤러 또는 Notifier
- Domain: 핵심 모델과 필요한 비즈니스 규칙
- Data: 로컬 데이터베이스, 저장소 구현, 데이터 매핑

작은 MVP에 과도한 추상화나 복잡한 디자인 패턴을 적용하지 않는다. 실제로 필요한 부분만 분리하고, 추후 기능 확장이 쉬운 수준으로 유지한다.

## 4. 상태 관리 규칙

Riverpod을 사용해 화면 상태와 데이터 흐름을 관리한다.

- 위젯에서 데이터베이스를 직접 호출하지 않는다.
- 데이터 조회 및 변경은 Repository를 통해 처리한다.
- 화면 상태는 필요한 범위에서만 관리한다.
- 화면이 종료되거나 다시 열려도 유지해야 하는 데이터는 영속 저장소에 보관한다.
- 일시적인 애니메이션 상태와 입력 중인 폼 상태는 불필요하게 데이터베이스에 저장하지 않는다.
- 비동기 처리 중 로딩, 오류, 빈 목록 상태를 명시적으로 처리한다.

단순한 화면 상태까지 복잡한 전역 상태로 만들지 않는다.

## 5. 데이터 모델 및 로컬 저장

초기 버전은 서버 없이 로컬 우선 구조로 개발한다.

다음 데이터를 영속 저장한다.

### AccountSettings
- id
- accountNickname
- virtualBalance
- currencyCode
- createdAt
- updatedAt

### MoodEntry
- id
- moodType
- createdAt

### DreamItem
- id
- title
- description
- estimatedCost: nullable
- createdAt
- updatedAt

### FutureLetter
- id
- title
- content
- createdAt
- unlockAt: nullable
- updatedAt

### AppSettings
- themeMode
- onboardingCompleted
- 기타 최소한의 사용자 설정

실제 데이터베이스 스키마를 설계할 때 필드의 null 허용 여부, 기본값, 인덱스 및 마이그레이션 전략을 명시한다.

기본 가상 잔고는 ₩1,000,000,000으로 설정한다. 가상 잔고는 실제 금융 자산이 아니며, 실제 은행 계좌나 결제 시스템과 연결하지 않는다.

초기 앱 실행 시 기본 데이터를 안전하게 생성하고, 앱을 재실행해도 사용자 데이터가 중복 생성되거나 초기화되지 않도록 한다.

데이터베이스 구조가 변경될 경우 마이그레이션을 고려한다. 단순히 앱 업데이트 과정에서 기존 사용자 데이터가 삭제되는 방식은 사용하지 않는다.

## 6. 로컬 데이터 관리 및 개인정보

- 로그인과 회원가입은 초기 버전에서 구현하지 않는다.
- 외부 서버에 개인 데이터를 전송하지 않는다.
- 사용자가 작성한 편지와 꿈 기록은 기본적으로 기기에 저장한다.
- 앱을 삭제하거나 기기를 변경하면 로컬 데이터가 사라질 수 있음을 고려한다.
- 초기 버전에서는 클라우드 동기화를 구현하지 않는다.
- 실제 금융 정보, 계좌번호, 카드번호 등은 수집하지 않는다.
- 오류 로그에 편지 내용 등 사용자의 사적인 텍스트를 남기지 않는다.

추후 백업 및 동기화 기능을 추가할 수 있도록 데이터 접근 책임은 Repository로 분리한다.

## 7. UI 및 디자인 시스템

DreamBank의 디자인은 고급 프라이빗 뱅킹과 감성적인 웰니스 앱의 중간 지점을 목표로 한다.

### 디자인 토큰

색상, 글꼴 크기, 간격, 모서리 반경, 그림자 및 애니메이션 지속 시간은 공통 테마와 디자인 토큰으로 관리한다.

- Primary: 딥 네이비
- Background: 블랙 또는 다크 네이비
- Accent: 절제된 골드
- Surface: 카드와 콘텐츠 영역을 구분하는 어두운 중간색
- Text Primary: 밝은 아이보리 또는 흰색
- Text Secondary: 대비가 충분한 회색

색상은 개별 위젯마다 직접 하드코딩하지 않는다.

### UI 품질 기준

- 가상 잔고는 홈 화면에서 가장 눈에 띄어야 한다.
- 숫자는 통화 형식에 맞게 천 단위 구분 기호를 사용한다.
- 버튼, 카드, 입력 폼의 스타일을 일관되게 유지한다.
- 작은 화면과 큰 화면에서 레이아웃이 깨지지 않아야 한다.
- 시스템 글자 크기 변경을 고려한다.
- 터치 영역과 텍스트 대비를 충분히 확보한다.
- 불필요한 애니메이션과 무거운 시각 효과를 피한다.
- 로딩, 오류, 빈 상태 및 저장 완료 피드백을 제공한다.

## 8. 가상 계좌 카드 이미지 생성 및 공유

계좌 공유 기능은 다음 방식으로 구현한다.

1. 앱 내부에서 공유용 카드 UI를 구성한다.
2. 카드 영역을 이미지로 렌더링한다.
3. 이미지 파일을 임시 디렉터리에 저장한다.
4. 운영체제의 공유 시트를 열어 다른 앱으로 전달한다.
5. 임시 파일이 불필요하게 누적되지 않도록 관리한다.

공유 카드에는 다음 정보를 표시한다.

- DreamBank 브랜드
- 계좌 별칭
- 가상 잔고
- 짧은 메시지
- 실제 금융 계좌가 아님을 알리는 표시

이미지 생성 로직과 운영체제 공유 기능을 분리한다. 이미지 생성 실패나 공유 취소가 앱 전체 오류로 이어지지 않도록 한다.

공유 카드의 레이아웃과 숫자는 실제 화면과 일치해야 한다.

## 9. 오류 처리 및 로깅

- 사용자에게 보여줄 오류 메시지와 개발자용 오류 정보를 분리한다.
- 로컬 저장 실패, 이미지 생성 실패, 데이터 조회 실패를 처리한다.
- 오류를 무시하거나 성공으로 간주하지 않는다.
- 개발 환경에서는 원인 파악에 필요한 로그를 남긴다.
- 운영 환경에서는 불필요한 상세 로그를 제한한다.
- 개인정보 및 사용자가 작성한 콘텐츠는 로그에 기록하지 않는다.

## 10. 테스트 기준

### 단위 테스트
- 잔고의 통화 표시 형식
- 초기 데이터 생성
- Repository의 CRUD 동작
- 편지 열람 가능 날짜 판정
- 기분에 따른 메시지 선택
- 데이터 저장 및 재조회

### 위젯 테스트
- 홈 화면의 가상 잔고 표시
- 마음 상태 선택
- 꿈 추가 및 목록 표시
- 편지 작성 및 목록 표시
- 계좌 별칭 수정
- 빈 상태 및 오류 상태 표시

### 통합 테스트
가능한 범위에서 다음 주요 흐름을 검증한다.

- 앱 최초 실행
- 꿈 작성 후 앱 재실행
- 편지 작성 후 재조회
- 계좌 별칭 수정
- 공유 카드 생성

모든 테스트가 실제로 통과했는지 확인하고, 실행하지 않은 테스트를 통과했다고 보고하지 않는다.

## 11. 코드 품질 기준

- `flutter analyze`의 오류를 해결한다.
- 의미 없는 `dynamic` 사용을 지양한다.
- null safety를 준수한다.
- 중복 코드를 공통 위젯이나 함수로 정리한다.
- 함수와 클래스는 명확한 책임을 갖도록 한다.
- 불필요한 전역 변수와 싱글턴을 지양한다.
- 사용하지 않는 의존성과 코드를 정리한다.
- 비즈니스 규칙을 UI 코드에 과도하게 섞지 않는다.
- 주요 비즈니스 로직에는 필요한 테스트를 작성한다.
- 코드 포맷을 일관되게 유지한다.

## 12. 빌드 및 배포 기준

### Android
- Android 디버그 빌드가 성공해야 한다.
- 릴리스 APK 또는 AAB를 생성할 수 있어야 한다.
- 패키지 식별자는 임의로 확정하지 말고 프로젝트 설정에서 관리한다.
- 서명 키와 비밀번호를 Git 저장소에 포함하지 않는다.

### iOS
- Xcode 프로젝트 설정이 정상이어야 한다.
- 시뮬레이터 빌드 및 실행을 검증한다.
- 실제 기기 배포를 위해 Bundle Identifier와 서명 설정을 관리한다.
- 인증서와 프로비저닝 프로파일은 안전하게 관리한다.
- App Store 배포용 아카이브를 만들 수 있도록 프로젝트를 구성한다.

Android와 iOS의 실제 빌드 여부를 각각 구분해 보고한다. 한 플랫폼에서 성공했다고 다른 플랫폼도 검증된 것으로 간주하지 않는다.

스토어 등록과 배포에 필요한 계정 및 인증 정보가 없는 경우 이를 명확히 보고하고, 임의의 인증 정보를 만들지 않는다.

## 13. 성능 및 안정성

- 앱 실행 시 불필요한 초기 작업을 줄인다.
- 작은 데이터셋을 위해 서버나 복잡한 캐시 시스템을 도입하지 않는다.
- 리스트는 데이터 규모에 맞게 효율적으로 렌더링한다.
- 불필요한 위젯 재빌드와 대규모 객체 생성을 줄인다.
- 화면 이동 및 애니메이션이 자연스럽게 동작하도록 한다.
- 데이터 저장 중 화면이 멈추지 않도록 비동기 작업을 적절히 처리한다.

초기 MVP에서 성능 최적화 프레임워크를 과도하게 도입하지 않는다. 실제 문제가 관찰되면 측정 후 개선한다.

## 14. CI 및 개발 자동화

초기 개발에서는 Git을 기본으로 사용한다.

CI를 추가할 경우 다음 검증을 자동화할 수 있도록 구성한다.

1. 의존성 설치
2. 코드 포맷 검사
3. 정적 분석
4. 단위 및 위젯 테스트
5. Android 빌드
6. 가능한 환경에서 iOS 빌드

CI 구성은 앱의 기본 구현과 로컬 빌드 검증이 완료된 뒤 필요한 범위에서 추가한다. 초기부터 복잡한 배포 자동화 시스템을 구축하지 않는다.

## 15. 작업 진행 방식

다음 순서로 작업한다.

1. 현재 컴퓨터에 설치된 Flutter, Dart, Android SDK, Xcode 환경을 확인한다.
2. `flutter doctor` 등 적절한 명령으로 개발 환경을 점검한다.
3. 기존 프로젝트가 있다면 구조와 설정을 확인한다.
4. 프로젝트 생성 및 필수 의존성을 구성한다.
5. 폴더 구조, 라우팅, 테마, 상태 관리 및 데이터베이스를 설정한다.
6. P0 기능을 구현하고 테스트한다.
7. P1 기능을 구현하고 테스트한다.
8. Android 빌드를 검증한다.
9. macOS 및 Xcode 환경이 갖춰져 있다면 iOS 빌드도 검증한다.
10. 남은 오류와 제한 사항을 정리한다.

각 단계가 끝나면 변경 파일, 실행한 테스트, 빌드 결과를 확인한다. 실패한 작업을 성공했다고 보고하지 않는다.

## 16. 최종 완료 보고

작업 완료 시 다음 내용을 요약한다.

- 선택한 기술 스택과 버전
- 최종 프로젝트 구조
- 구현된 기능
- 로컬 데이터베이스 구조
- 주요 의존성 및 도입 이유
- 테스트 실행 결과
- Android 빌드 결과
- iOS 빌드 결과
- 현재 알려진 문제
- 실제 기기 테스트 및 스토어 출시를 위해 남은 작업

문서만 작성하고 종료하지 않는다. 실제 파일을 생성하고 코드 구현과 검증을 수행한다.

이 스펙을 DreamBank의 기술 기준으로 적용하되, 구현에 필요하지 않은 추상화와 복잡성을 추가하지 말고 작동하는 MVP를 우선 완성하라.
